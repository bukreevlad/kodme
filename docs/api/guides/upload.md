# Загрузка файлов

Файлы (вложения сообщений и комментариев, стикеры, аватарки, обложки,
файлы облака)
загружаются не через WebSocket, а напрямую в S3-совместимое хранилище по
presigned **POST policy**. WebSocket-канал используется только для подготовки
загрузки и для финального сохранения.

## Схема обработки

Для **всех** файлов (вложения сообщений и комментариев, стикеры, аватарки,
обложки, файлы облака) производные ассеты (превью, LQIP, цвета, осциллограмма,
метадата) **генерирует сервер** после загрузки: клиент заливает **только
оригинал**, а событие сохранения (`save attach` / `save sticker` /
`save avatar` / `save thumb` / `save file`) проверяет оригинал и отвечает
«готово» только после обработки. Клиент готовит файл и его `metadata`-флаги,
но не производные.

## Схема загрузки

```
Клиент ──WS──► «get upload ... url» ──► Ответ: { targets, document_id }
Клиент ──POST──────────────────────────► target.url (multipart: поля target.fields
                                         + файл под ключом "file")
  └─► 204 No Content от S3
Клиент ──WS──► «save attach» / «save sticker» / «save avatar» / … ──► { document_id, status: "ready" }
                 (сервер обрабатывает файл и подтверждает)
Клиент ──WS──► использование document_id (send / привязка аватарки / …)
```

### Шаг 1. Запросить ссылку

События подготовки зависят от типа файла:

| Назначение | Событие | Обязательные поля |
| --- | --- | --- |
| Вложение сообщения | `[message]: get upload attach url` | `{ channel_id, file_name, mime_type, size, metadata }` |
| Вложение комментария | `[comment]: get upload attach url` | `{ channel_id, file_name, mime_type, size, metadata }` |
| Стикер | `[sticker]: get upload sticker url` | `{ pak_id, file_name, mime_type, size, metadata }` |
| Аватар профиля | `[user]: get upload avatar url` | `{ file_name, mime_type, size }` |
| Аватар канала | `[channel]: get upload avatar url` | `{ channel_id, file_name, mime_type, size }` |
| Аватар группы | `[group]: get upload avatar url` | `{ channel_id, file_name, mime_type, size }` |
| Аватар темы группы | `[group-topic]: get upload avatar url` | `{ channel_id, file_name, mime_type, size }` |
| Обложка трансляции | `[broadcast]: get upload thumb url` | `{ cast_id, file_name, mime_type, size }` |
| Обложка конференции | `[meet]: get upload thumb url` | `{ meet_id, file_name, mime_type, size }` |
| Файл в облако | `[cloud]: get upload file url` | `{ folder_id, file_name, mime_type, size }` |

Поля:

- `file_name` — оригинальное имя файла;
- `mime_type` — MIME-тип (например, `image/jpeg`). Обязателен: сервер сверяет
  его с расширением имени файла;
- `size` — размер файла в байтах, целое число. Обязателен: размер участвует в
  подписи загрузки, и без него запрос отклоняется (`FILE_SIZE_REQUIRED`);
- `metadata` — метадата файла, нужна только **вложениям сообщений и
  комментариев и стикерам**: производные создаёт сервер, здесь достаточно
  `null` (или объекта с флагами, например голосовой заметки). Для
  **аватарок, обложек и облака** поле не передаётся — производные ассеты
  создаёт сервер, формат метадаты см. в
  [контракте метадаты v2](../websocket/client-to-server/storage.md#метадата-файла-контракт-v2).

Ответ:

```json
{
  "document_id": "UUIDv7",
  "targets": [
    {
      "path": "messages/attaches/<channel_id>/<uuid>/<uuid>.jpg",
      "kind": "original",
      "url": "https://s3.kodme.ru/kodme",
      "fields": {
        "Content-Type": "image/jpeg",
        "bucket": "kodme",
        "X-Amz-Algorithm": "AWS4-HMAC-SHA256",
        "X-Amz-Credential": "…",
        "X-Amz-Date": "…",
        "key": "messages/attaches/<channel_id>/<uuid>/<uuid>.jpg",
        "Policy": "…",
        "X-Amz-Signature": "…"
      },
      "mime_type": "image/jpeg",
      "max_size": 524288000
    }
  ]
}
```

- `targets[]` — набор целей загрузки, по одной на объект. Выдаётся **только
  оригинал** (`kind: "original"`) — производные ассеты (превью, рендерации)
  создаёт сервер после загрузки. Ориентируйтесь на `kind`, а не на порядок
  в массиве. Загрузить нужно **каждую** цель.
- `mime_type` — MIME, под которым объект подписан в S3 (`image/webp` у превью,
  `video/mp4` у рендераций); `max_size` — верхняя граница размера. У
  производных она с запасом ±4096 байт к заявленному в метадате размеру.
- `fields` — поля подписанной политики. Отправьте в форме **все** поля объекта
  (перебирая его целиком), **до** файла и в порядке, в котором они пришли.
  Не читайте поля по именам из примера: состав и регистр имён задаёт
  подписываемая политика и может отличаться — контракт именно в том, что
  нужно отправить ровно тот объект, который вернул сервер.
- Лимиты на загрузку (максимальный размер в байтах, число файлов на
  сообщение, максимальная длина имени, справочник допустимых типов файлов)
  приходят при авторизации — поля `limits` и `file_types` ответа
  [`POST /auth/check`](../http/auth.md). Не храните свою копию лимитов —
  берите их оттуда.
- `document_id` «зарезервирован» под текущего пользователя и сущность
  (канал/пользователя/трансляцию) на время жизни записи (порядка часа).
  Использовать его в `send`/`save` нужно до истечения срока.

### Шаг 2. Загрузить файл

`POST` на `target.url` мультипарт-формой:

```
Content-Type: multipart/form-data; boundary=…   (браузер выставит сам)

--boundary
Content-Disposition: form-data; name="key"
…(значения всех полей из target.fields — каждое отдельной частью, до файла)…

--boundary
Content-Disposition: form-data; name="file"; filename="…"
Content-Type: (MIME файла)
…тело файла…
--boundary--
```

Успех — **`204 No Content`**. Ошибки политики: `400` (размер за пределами
диапазона), `403` (чужой ключ / несовпадение MIME с подписанным).

Не задавайте `Content-Type` заголовком вручную: он обязан быть
`multipart/form-data; boundary=…`, сгенерированным вашей HTTP-библиотекой.

### Шаг 3. Сохранить

Событие сохранения обязательно для **всех** файлов:

- Вложения сообщений и комментариев (без него `send` отклоняется):
  - Сообщение: `[message]: save attach` с `{ "document_id": "…" }`
    (см. [messages.md](../websocket/client-to-server/messages.md)).
  - Комментарий: `[comment]: save attach` с `{ "document_id": "…" }`
    (см. [comments.md](../websocket/client-to-server/comments.md)).
  - Стикер: `[sticker]: save sticker` с `{ "pak_id": "…", "document_id": "…"}`
    (см. [stickers.md](../websocket/client-to-server/stickers.md)).
- Аватар: `[user]: save avatar` / `[channel]: save avatar` /
  `[group]: save avatar` / `[group-topic]: save avatar` /
  `[bot]: save avatar` с `{ "document_id": "…" }`.
- Обложка: `[broadcast]: save thumb` / `[meet]: save thumb` с
  `{ "document_id": "…" }`.
- Облако: `[cloud]: save file` с `{ "document_id": "…" }`.

Сервер проверяет, что оригинал реально загружен и его размер совпал с
заявленным, затем генерирует производные ассеты и отвечает
`{ "document_id": "…", "status": "ready" }` (обложки и аватарки —
токенизированный объект файла). Обработка занимает время — таймаут
запроса должен быть **не меньше 120 секунд**. Повторный вызов с тем же
`document_id` безопасен (идемпотентен): уже готовый файл отвечает сразу —
можно спокойно повторять при сетевом таймауте.

Если производные ассеты создать не удалось, `save attach` отвечает
`"processed": false` (опционально с `"reason": "failed"`) — это не ошибка:
отправляйте сообщение/комментарий как обычно, вложение отобразится
документом для скачивания без превью (см.
[messages.md](../websocket/client-to-server/messages.md)). Аватарки,
обложки и стикеры в такой ситуации отвечают ошибкой — они без
производных ассетов не существуют.

Для вложений повторное использование без `save` невозможно: `send`
отвечает `DOCUMENT_NOT_PROCESSED` (122016), пока вложение не сохранено.

### Шаг 4. Использовать document_id

- Вложение в сообщение: `[message]: send` с
  `attachments: { "<document_id>": {} }` (до 10 файлов за сообщение).
- Вложение в комментарий: `[comment]: send` с `attachments`.

Сервер проверяет, что документ загружал именно текущий пользователь и для этой
же сущности, после чего «привязывает» файл.

## Обработка файлов

Сервер после события сохранения генерирует производные ассеты из реального
файла: превью, LQIP-плейсхолдер, акцентные цвета, форму волны для аудио,
метадату (размеры, длительность, aspect ratio и пути). Готовая метадата
попадает в сообщение при `send` и в ответы `save` аватарок/обложек/файлов —
клиенту не нужно ничего вычислять.

## Ошибки

Ошибки подготовки загрузки приходят штатным образом (объект ошибки WebSocket)
с именем ошибки:

- `FILE_NAME_REQUIRED` / `FILE_NAME_TOO_LONG` — нет/битое/слишком длинное имя файла.
- `FILE_SIZE_REQUIRED` — не передан размер.
- `INVALID_FILE_SIZE` — размер не целое число байт или вне допустимого диапазона.
- `MIME_TYPE_REQUIRED` — не передан MIME.
- `INVALID_MIME_TYPE` — MIME вне справочника.
- `MIME_EXTENSION_MISMATCH` — MIME не совпадает с расширением имени файла.
- `INVALID_EXTENSION` — расширение имени файла вне белого списка.
- `INVALID_METADATA` — метадата слишком глубокая/большая.
- `INVALID_MEDIA_METADATA` (`124244`) — метадата не прошла белый список.
- `INVALID_PLACEHOLDER` (`124245`) — LQIP больше 4096 байт.
- `ACCESS_DENIED` — нет права на запись (нет права отправлять сообщения в канал
  и т.п.).

Ошибки сохранения вложения (`save attach`, коды сообщения / комментария):

- `DOCUMENT_NOT_FOUND` (`136100` / `136200`) — запись загрузки не найдена
  (истёк срок жизни или запрос пришёл позже).
- `MEDIA_PROCESSING_FAILED` (`136101` / `136201`) — обработка файла не
  уложилась в отведённое время (она ещё идёт); повторите вызов — ожидающий
  файл дождётся результата. Сам неудачный результат — не ошибка: `save`
  отвечает `"processed": false` (см. [шаг 3](#шаг-3-сохранить)).
- `OBJECT_NOT_UPLOADED` (`136102` / `136202`) — оригинал не загружен в хранилище.
- `UPLOAD_SIZE_MISMATCH` (`136103` / `136203`) — фактический размер объекта не
  совпал с заявленным.
- `DOCUMENT_ID_REQUIRED` / `DOCUMENT_ID_INVALID` (`136104` / `136105`,
  `136204` / `136205`) — не передан или битый `document_id`.
- `ACCESS_DENIED` (`136106` / `136206`) — загрузку завершает другой
  пользователь или без прав на публикацию.

Ошибки финального сохранения (`send`/`save`) после загрузки файлов:

- `DOCUMENT_NOT_PROCESSED` (`122016`) — вложение не прошло `save attach`
  (сообщение/комментарий не может быть отправлено с этим файлом).
- `DOCUMENT_NOT_FOUND` (`124250`) — документ не найден (истёк TTL и т.п.).
- `ACCESS_DENIED` (`124251`) — документ загружал другой пользователь или для
  другой сущности.
- `UPLOAD_SIZE_MISMATCH` (`124254`) — фактический размер объекта в S3 не
  совпал с заявленным.
- `UPLOAD_MIME_MISMATCH` (`124255`) — фактический MIME объекта не согласуется
  с расширением и заявленным MIME.
- `THUMBNAIL_MISSING` (`124256`) — превью заявлено, но не докачано.
- `RENDITION_MISSING` (`124257`) — рендерация заявлена, но не докачана.
- `OBJECT_NOT_UPLOADED` (`124258`) — объект не загружен.
- `MEDIA_PROCESSING_FAILED` (`124259`) — обработка файла не удалась или не
  уложилась в отведённое время; повторите событие сохранения ещё раз.
- `MEDIA_PROCESSING_DISABLED` (`124260`) — серверная обработка файлов
  временно отключена: аватар, обложку или стикер сохранить нельзя
  (вложения в это время отправляются без превью — `processed: false`).

Полный список кодов — в
[разделе storage](../websocket/client-to-server/storage.md#ошибки).

## Скачивание

Готовые файлы клиент получает как токенизированный объект
[File](../objects/file.md) и скачивает по HTTP
`GET /api/v1/storage/:document` (см. [http/storage.md](../http/storage.md)).
